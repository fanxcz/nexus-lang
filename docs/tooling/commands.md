# Tooling Commands

The CLI reference below matches the commands implemented by NEXUS 1.1.0. Options that are not listed here should not be assumed to exist; unsupported options produce an error.

## Interactive terminal

Run `nexus` with no arguments or use `nexus repl` to enter the interactive shell.
Each expression is compiled and evaluated by NEXUS; `let`/`const` bindings and simple
assignments remain available in subsequent entries. The shell accepts NEXUS syntax, not
Python syntax. Use `:help`, `:vars`, `:history`, `:history-clear`, `:clear`, or `:quit` inside the shell.

Submitted input is persisted between launches (the most recent 500 entries). On Linux/macOS
it defaults to `~/.nexus_repl_history`; on Windows it defaults to `%APPDATA%\\NEXUS\\repl_history.txt`.
Set `NEXUS_HISTORY_FILE` to choose a different file, for example for an isolated project or test.

```text
nexus> 2 + 2
4
nexus> let mut answer = 21
nexus> answer * 2
42
```

## Project workflow

| Command | Purpose |
|---|---|
| `nexus new <project> [--template NAME]` | Create a project in a new directory |
| `nexus init [--template NAME]` | Initialize the current directory |
| `nexus info` | Print the current project's manifest settings |
| `nexus assets` | List files in known asset and scene directories |
| `nexus clean` | Remove the project's `build/` directory |
| `nexus doctor [--json]` | Report runtime, standard library, template and compiler availability |
| `nexus self-test` | Compile and run a tiny program, preferring the built-in backend where supported |
| `nexus editor [--gui]` | Generate VS Code workspace files, or run the built-in editor with `--gui` |

Supported project templates: `cli`, `app`, `game`, `3d`, `paint`, `server`, and `library`.

## Build and run

```bash
# Create, build, and run a project
nexus new HelloNexus --template cli
cd HelloNexus
nexus check
nexus build --release
nexus run --release

# Compile one source file
nexus build src/main.nx -o hello --backend auto

# Ask which backend will be selected
nexus explain-backend src/main.nx
nexus explain-backend src/main.nx --target x86_64-linux

# Print supported target names
nexus targets
```

The built-in machine-code backend avoids external compiler tools for its supported x86-64 Windows/Linux subset. The LLVM fallback is required for programs outside that subset and for targets supported through the configured Clang toolchain. Listing a target does not mean the built-in backend can emit it.

## Windows console output

When you run `nexus run file.nx` from an already-open terminal, the output remains in that terminal. To run a source file from File Explorer, use the NEXUS context-menu action **Run with NEXUS**; the installed launcher waits for Enter after the program ends so you can read its output. The standalone `Run-NAME.bat` generated by `nexus build file.nx` does the same for a compiled `.exe`.

Double-clicking a console `.exe` directly is normal Windows behavior: the console window can close as soon as the process exits. Open the accompanying `Run-NAME.bat` instead when you need the final output to stay visible. The compiled `.exe` itself is not forced to pause, so command-line tools remain usable from scripts and other terminals.

Supported build flags:

- `nexus build [file.nx] [-o OUTPUT] [--target TRIPLE] [--backend auto|native|llvm] [--emit-ir] [--release]`
- `nexus run [file.nx] [--target TRIPLE] [--backend auto|native|llvm] [--release]`
- `nexus export [--target TRIPLE] [--backend auto|native|llvm] [-o OUTPUT]`

## Code quality

```bash
# Format the current project entry (or one file)
nexus fmt
nexus fmt src/main.nx

# Check without changing the file; exits nonzero if changes are needed
nexus fmt --check src/main.nx

# Parse and run semantic checks
nexus check src/main.nx
nexus lint src/main.nx

# Generate API documentation from the project's entry file
nexus doc
```

The formatter's `--check` mode never writes to the file. The formatter is deliberately modest; it is not yet a full syntax-aware pretty-printer. `nexus fmt --all` formats `.nx` files in the project recursively, while `nexus fmt --check --all` checks every discovered source without modifying it. Both skip `.git`, `.vscode`, `build`, `dist`, `vendor`, `node_modules`, `CMakeFiles`, `target`, and `.cache`. `lint` performs the current line-level checks and semantic analysis; it does not accept a configurable rule set or JSON output option.

## Testing and profiling

```bash
# Project test programs are read from tests/programs/
nexus test

# Compile and run a self-contained built-in-backend check
nexus self-test

# Run a source program repeatedly (default: five runs)
nexus bench src/main.nx --runs 10
```

`nexus test` builds and runs each `.nx` file beneath the project's `tests/programs/` directory. It reports no tests when that directory is absent. For compiler development, use the repository's CMake/CTest suite as documented in [Building from Source](../development/building.md).

## Package commands

```bash
nexus pkg init
nexus pkg add ../my-library
nexus pkg list
nexus pkg remove my-library
nexus pkg update
nexus pkg build
nexus pkg publish
```

The current package manager supports local vendoring and creation of a local `.nxpkg` archive. `publish` does not upload to a hosted package registry. `nexus pkg verify` validates local package checksums and checks that manifest dependencies, lockfile entries, versions, and paths under `vendor/` agree.

## Language server

Run `nexus lsp` from an editor configured to launch the language server over standard input/output. The server provides diagnostics, completion, signature help, hover, go-to-definition, references, rename, whole-document and range formatting, quick fixes, a current-file Outline (`textDocument/documentSymbol`), and workspace-wide declaration search (`workspace/symbol`). Workspace files are cached and indexed for supported declarations, including unopened `.nx` files; workspace symbol search is capped at 500 results per request. Resolution is still lexical rather than a full type-aware semantic model: struct fields, enum variants, import aliases, and inferred types have known limitations.

## Diagnostics

```bash
nexus doctor
nexus doctor --json
```

The JSON form is intended for scripts. It emits booleans describing detected compiler, runtime, standard library, templates, and project availability. A missing LLVM compiler is not by itself fatal because supported source programs can use the built-in backend.

## General

```bash
nexus --help
nexus --version
```

See the [NEXUS Roadmap](../development/roadmap.md) for planned improvements and completion criteria.


REPL history persists between launches (up to 500 entries); `:history-clear` removes saved entries too. Terminal arrow-key editing is not yet provided.


State is rebuilt from saved declarations and statements for each entry. Pure `if`, `while`, `for`, and `match` blocks that only use local expressions and assignments are retained so their binding changes persist. Blocks containing function calls or unsupported operations run once but are not replayed; the shell prints a note because mutations inside those blocks cannot currently be retained.


## LSP signature help

The language server provides function signatures while the cursor is inside a call. It reports parameter names and types for user-defined functions across the current workspace, and type-based parameter hints for built-ins whose signatures are defined by the runtime. Nested parentheses, array expressions, and struct literals do not incorrectly increase the outer call's active parameter.
