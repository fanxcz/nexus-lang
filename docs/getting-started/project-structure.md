# Project Structure

NEXUS projects are intentionally simple. Start with the checked-in CLI or app
template, then add modules and resources only as your program needs them.

## Create a project

For a native windowed application:

    nexus new MyApp --template app
    cd MyApp
    nexus check
    nexus build
    nexus run

For a terminal utility, use nexus new MyTool --template cli. The CLI copies
one starter source file; it does not generate a multi-file framework.

## Generated layout

The project generator creates a manifest, source entry point, standard
resource folders, a scene-data placeholder, README, and .gitignore. A typical
project grows into this shape:

~~~text
MyApp/
├── nexus.toml          # Project/build manifest
├── README.md           # Project notes
├── .gitignore
├── src/
│   └── main.nx         # Entry point for a generated project
├── assets/             # Resources used by the application
├── scenes/
│   └── main.nxs        # Scene-data placeholder generated by the template
├── tests/              # Optional test source files
├── vendor/             # Local packages added with nexus pkg add
├── nexus.lock          # Generated when the local package workflow needs it
└── build/              # Generated build output
~~~

Only files and folders actually generated by the selected template should
be assumed to exist. Add tests/, vendor/, or extra .nx modules as needed.
Do not expect the template to create a ready-made scene graph, asset pipeline,
GUI framework, or multi-module application architecture.

## The manifest

The nexus.toml file identifies the package and its build entry. The following
is the minimal shape used in the current local-package workflow:

~~~toml
[package]
name = "my-library"
version = "1.0.0"

[build]
entry = "src/main.nx"
artifact = "my-library"
target = "native"
~~~

The application/project generator may write additional metadata. Only use
manifest fields documented by the current CLI and package manager; do not
assume settings for arbitrary linkers, LTO profiles, or cross-compilation
targets are supported simply because similar options exist in other tools.

Use nexus info to inspect the project metadata and nexus doctor to check the
local compiler/runtime setup.

## Source modules and imports

Keep the entry point in src/main.nx and split reusable code into separate
source files. The current compiler supports file-based imports and standard
library imports, for example:

~~~nx
import std.fs
import std.math
import "helpers.nx"

fn main() {
    print(math_floor(3.8))
}
~~~

The compiler loads acyclic source imports once and reports circular imports
with a path trace. It does not support Rust-style module/export declarations
or package-wide workspace manifests. Use the actual import forms shown in the
Modules and Imports reference.

## Assets and resources

The CLI includes an nexus assets command for inspecting project resources.
Image, font and audio loading is performed by runtime APIs and can depend on
optional host libraries. Keep relative paths consistent with the working
directory from which the program is launched.

Resource copying and packaging should not be assumed to happen automatically
for every custom file. For a distributable app, use the official packaging
workflow as the reference and test the result from a clean directory or
machine. Reproducible custom-resource packaging remains a roadmap area.

## Build output

Run nexus build for a normal build or nexus build --release for an optimized
build. Generated artifacts are written under build/; the release project smoke
test verifies a path under build/release/. On Windows, executables use the
.exe suffix.

Common commands:

    nexus check
    nexus build
    nexus build --release
    nexus run
    nexus fmt --all
    nexus fmt --check --all
    nexus lint
    nexus info

Run commands from the project root unless a command explicitly accepts a
source-file path. See the command reference for current command behavior.

## Local packages

The package workflow currently supports local source packages:

    nexus pkg add ../my-library
    nexus pkg list
    nexus pkg verify
    nexus pkg remove my-library

Packages are copied into vendor/, and the consuming project's manifest and
lockfile are updated. The package manager does not currently provide an online
registry, dependency version solving, Git dependencies, or transitive builds.
See Creating Packages for the supported local manifest and Using Packages for
local dependency management.
